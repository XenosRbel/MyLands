# Общий процесс Codex и Claude Code

## Начало задачи

1. Прочитай `AGENT.md` и обязательные документы из его раздела Before you start.
2. Выполни `make harness-context`.
3. Выбери карточку `tasks/T-*.md`.
4. Запиши относительный путь карточки в `.harness/current-task`.
5. Прочитай подходящий проектный skill.
6. Используй MCP-граф для поиска реализации, тестов и вызывающего кода.
7. При недоступном графе укажи причину перехода к файловому поиску.

## Выполнение

- Выполняй согласованный объём задачи в выбранной ветке.
- Перед изменением прочитай файл и связанные тесты.
- Для нового поведения сначала воспроизведи ожидаемую ошибку тестом.
- Для крупных изменений зафиксируй дизайн и план.
- Рутинные исправления выполняй без дополнительного согласования.
- Делегируй только при явном запросе или применимом требовании skill.
- Не расширяй разрешения инструмента автоматически.
- Не считай инструкцию или хук полноценной границей безопасности.

## Завершение

1. Выполни `make harness-check`.
2. Для пользовательского потока выполни `make e2e` против работающего сервера.
3. Обнови документацию, затронутую изменением.
4. Запиши результат и ограничения в карточку задачи.
5. Сопоставь каждый критерий приёмки с фактически выполненной проверкой.
6. Перечисли непроверенные пункты и причины.

Не объявляй задачу завершённой при обязательных красных проверках.
Не отключай тесты ради зелёного результата.
Повторный Stop может завершить диалог после ошибки, но не подтверждает готовность изменения.
Не утверждай, что ручная проверка доказывает загрузку хуков клиентом.

## Сложность задачи

Источник идеи: [статья на Habr](https://habr.com/ru/articles/1098168/).
Посчитай признаки до начала работы.
Каждый выполненный пункт даёт один признак:

- Изменение затрагивает два слоя или больше (сервер, клиент, Game Pack, БД).
- Изменение меняет существующую логику.
- Рядом находятся вход, права, ресурсы или платежи.
- Карточка содержит три подзадачи или больше.
- Одна подзадача блокирует другую.
- Изменение затрагивает пять файлов кода или больше.

Правило выбора:

- 0–1 признак: задача простая. Дополнительные роли не нужны.
- 2–3 признака: запиши план в карточку. Предложи пользователю роль Principal Architect.
- 4 признака или больше: задача сложная. Запроси заключение Principal Architect до первой правки.

Запиши число признаков в карточку. Не меняй оценку по ходу спора.

## Независимая приёмка

Заявление «готово» от исполнителя считается кандидатом, а не результатом.
Приёмку выполняет отдельный проверяющий с чистым контекстом.
Проверяющий видит раздел «Критерии приёмки» карточки и diff задачи.
Он проходит критерии по одному.
Он не читает рассуждения исполнителя.
Первая непустая строка отчёта содержит только `ACCEPT: PASS` или `ACCEPT: FAIL`.
Остальные строки сопоставляют критерии с проверками.
Основной агент не меняет вердикт.
Делегируй приёмку только при явном запросе пользователя.
Без делегирования выполни тот же проход критериев сам и укажи это в карточке.

## Статус и восстановление

Поле «Результат» карточки содержит одно слово из списка: `Открыта`, `В работе`, `Готово`, `Заблокирована`.
Пояснения записывай отдельной строкой ниже.
Первая причина блокировки идёт в поле «Ограничения».
После сжатия контекста восстановись по `.harness/current-task`, карточке и `make harness-context`.
Не полагайся на память диалога.

## Команды

- `make harness-context`: ветка, изменения и текущая задача.
- `make harness-doctor`: зависимости и конфигурация без установки пакетов.
- `make harness-test`: автономные тесты harness.
- `make harness-check`: harness, lint, Go с БД и race, клиентские тесты, Game Packs.
- `python3 scripts/harness/harness.py check`: те же проверки с таймаутом и журналом `.harness/check.log`.

Подробности и ограничения: `docs/AGENT_HARNESS.md`.

## Роли

Principal Architect: `.agents/roles/principal-architect.md`.
Роль анализирует архитектуру, корректность, надёжность и измеримую производительность.
Она возвращает заключение; основной агент реализует изменения и ведёт карточку задачи.
Пример: «Используй Principal Architect для оценки 1000 CCU на одном экземпляре».
Адаптеры клиентов и ограничения описаны в `docs/AGENT_HARNESS.md`.
