# Один экземпляр: цель 1000 одновременно онлайн

Дата: 2026-11-01.
Статус: PROPOSED; архитектурный обзор, не результат нового нагрузочного теста.
Связанная задача: [T-033](../../tasks/T-033.md).

## Целевая среда

Данные предоставлены пользователем:

- 1000 одновременно активных игроков в первый месяц.
- Один домашний сервер с Intel Core i7-7700 @ 3.60 GHz.
- 40 ГБ оперативной памяти.
- PostgreSQL на SSD NVMe.
- Интернет 250 Мбит/с; фактический upload и симметричность канала пока не подтверждены.
- Несколько NVIDIA GPU; текущий Go/PostgreSQL-бэкенд их не использует.

Рассматривается один Go-процесс с API и воркером плюс одна PostgreSQL на той же машине.
Один процесс Go может выполнять независимую работу конкурентно.
Блокировка одного игрока сохраняет последовательность его изменений.
Ёмкость этой конфигурации пока не измерена.

## Что означает 1000 CCU

CCU означает число одновременно подключённых пользователей.
Оно не равно числу запросов или игровых команд в секунду.

Видимый клиент обновляет overview и выбранный город каждые 15 секунд.
Источник: [context.tsx](../../client/src/game/context.tsx), `refresh`, строки 101–133.

Модель для планирования, а не измерение:

| Сценарий | Расчёт | Поток |
|---|---|---|
| 1000 открытых клиентов, текущий polling | 1000 × 2 / 15 | около 133 HTTP-запросов/с |
| Команда каждого игрока раз в 30 секунд | 1000 / 30 | дополнительно около 33 команд/с |
| Команда каждого игрока раз в 10 секунд | 1000 / 10 | дополнительно около 100 команд/с |

Карта, рейтинги, вход, повторные запросы и события добавляют отдельную нагрузку.
Несколько вкладок одного игрока также увеличивают поток.
Нужны отдельные сценарии массового входа и одновременного завершения миссий.

Пример сетевого бюджета: пара ответов размером 50 КБ даёт около 26,7 Мбит/с при 1000 клиентах.
Размер 50 КБ здесь условный; реальные ответы и сжатие ещё не измерены.
Начальная загрузка графики и ресурсов может создавать гораздо более короткие пики.

## Что подтверждает существующий baseline

Источник: [нагрузочный отчёт](../reports/LOAD_TEST_2026-10-31.md).

- 200 виртуальных игроков, около 30 секунд, 648 HTTP-запросов/с.
- Сервер, генератор и PostgreSQL делили четыре vCPU.
- Ошибок 5xx и сети не зарегистрировано; воркер не накопил просроченные события в этом прогоне.
- Около 42% ответов были ожидаемыми 422; все тренировки отклонены из-за отсутствия казарм.
- Генератор уменьшает интенсивность при росте задержки: запросы выполняются последовательным циклом каждого игрока.
- Отдельный SQL поиска spawn ускорен с 55,1 до 5,9 ms; полный нагрузочный прогон после изменения не повторён.

Результат подтверждает короткий смешанный сценарий, а не вместимость 1000 CCU.
Новый прогон должен фиксировать версию кода, hash Game Pack, скорость мира и размер БД.

## Подтверждённые кандидаты для оптимизации

Эти факты описывают код. Их вклад в задержку и ожидаемое ускорение ещё не измерены.

| Чтения состояния | WithPlayer/WithCity блокируют игрока, settleLocked загружает города, save обновляет города и игрока | Уменьшить количество повторных транзакций; измерить SQL и WAL | Не отключать settlement и сохранение реально изменённой экономики |
| Game Pack | Pack читает pack_json до проверки кеша | Получать blob только при cache miss; отдельно проверять версию и speed | Корректная инвалидация после committed migration |

## Предлагаемый порядок

### Этап 1: достоверное измерение

1. Подготовить игроков с казармами, армиями, исследованиями и несколькими городами.
2. Разделить успешные чтения, успешные команды, бизнес-отказы, 429, 5xx и сетевые ошибки.
3. Отделить регистрацию и join от измеряемого игрового интервала.
4. Запускать генератор с другой машины; целевой сервер остаётся одним экземпляром.
5. Пройти ступени 200, 500 и 1000 CCU.
6. Провести длительный прогон и сценарии всплесков после прогрева.
7. Измерить p95/p99 HTTP, event lag, pool wait, длительность транзакций, CPU, RAM, диск и WAL.
8. Снять профили CPU, heap и contention по отдельности.

Go предоставляет соответствующие профили через pprof; некоторые профили влияют друг на друга.
Источник: [Go diagnostics](https://go.dev/doc/diagnostics).
Для SQL использовать pg_stat_statements и планы медленных запросов.
Подключение pg_stat_statements требует соответствующей настройки PostgreSQL и перезапуска.
Источник: [PostgreSQL 16](https://www.postgresql.org/docs/16/pgstatstatements.html).

Ориентир p95 <150 ms при 1000 игроках указан в прежнем нагрузочном отчёте.
Это целевой показатель, а не подтверждённый результат данного сервера.
Допустимую задержку событий и поведение при перегрузке нужно согласовать отдельно.

### Этап 2: убрать повторную работу

Сначала проверить объединение polling, SQL очередей и повторных вычислений CityView.
Следом проверить загрузку pack_json на cache hit.
Для каждого изменения сравнивать один и тот же сценарий до и после.
Сохранять integration, concurrency и идемпотентностные проверки.

### Этап 3: ограничить конкуренцию

Настраивать worker concurrency совместно с бюджетом API и пула PostgreSQL.
Сохранять последовательную обработку событий каждого игрока.
Существующий Process использует блокировку игрока с SKIP LOCKED.
SKIP LOCKED подходит для очередей, но не заменяет согласованное чтение общего состояния.
Источник: [PostgreSQL SELECT](https://www.postgresql.org/docs/16/sql-select.html).

Проверять насыщение, восстановление после всплеска и массовый возврат отсутствовавших игроков.
Не добавлять отдельный read model без явного контракта свежести.

## Домашний сервер

- Разместить PostgreSQL на NVMe и ограничить конкурирующий дисковый ввод-вывод.
- Выделить бюджеты CPU и RAM для игры, если на машине выполняются другие задачи.
- Проверить исходящий канал, задержку под нагрузкой и наличие доступного входящего подключения.
- Использовать HTTPS reverse proxy и кеширование статических ресурсов браузером.
- Проверить внешний доступ с учётом CGNAT, если он используется провайдером.
- Подготовить автозапуск, мониторинг, внешние резервные копии и проверку восстановления.
- Учесть питание и связь: один домашний узел остаётся единой точкой отказа.

Не отключать fsync и другие гарантии сохранности PostgreSQL ради результата benchmark.
Мощность GPU не увеличивает доступный CPU-бюджет API и транзакций.

## Альтернативы

1. Оптимизировать текущий монолит и одну PostgreSQL. Рекомендуется первым: минимальная эксплуатационная сложность.
2. Добавить отдельные read models или push-уведомления после измерений. Потребуются правила свежести, восстановления и backpressure.
3. Разнести процессы или машины после достижения измеренного предела. Это выходит за текущую цель одного экземпляра.

Redis, Kafka, Kubernetes и GPU-вычисления не требуются автоматически из-за числа 1000 CCU.
Их введение должно отвечать подтверждённому ограничению или требованию надёжности.
