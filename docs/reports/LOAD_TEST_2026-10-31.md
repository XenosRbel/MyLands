# Load test — 2026-10-31 (first baseline)

Harness: `server/cmd/loadtest` (Go). Each virtual player: guest sign-in → join world → loop every 200 ms over {city view, build, city view, train} with idempotency keys.
Environment: single 4-vCPU container running server, PostgreSQL 16 and the load generator together; pool 20 connections; world speed ×50; rate limits raised (`RF_RATE_RPS=100000`).

```

op          count      p50      p95      p99      max
build        4796     99ms    177ms    232ms    283ms
city         9562    102ms    190ms    301ms    409ms
train        4667     76ms    147ms    194ms    269ms

overview      200    773ms   1012ms   1031ms   1055ms
status: 200×11337, 422 insufficient_resources×3220, 422 requirements_not_met×4667 (no barracks — expected), 422 queue_full×401
metrics: events processed 1592, failed 0, overdue 0, parked 0, tx retries 0
```

Findings
1. Correctness held under load: zero server errors, no deadlock retries, worker kept up (0 overdue events).
2. **Join burst is slow** (p95 1.2 s): `findSpawn` scans tiles with a `NOT EXISTS` over cities and `ORDER BY random()`; 200 simultaneous joins also contend for spawn rows. Action: precomputed spawn rings or a cities spatial index (T-021 follow-up).
3. City view (~10 queries) dominates; p95 190 ms on shared hardware is acceptable for v0.1; candidates: merge queue queries, cache pack-derived views.

Not yet measured: separate DB host, 1 000+ players, long-running worker lag with many due events, mixed PvP traffic. Target from ROADMAP: 1 000 players, p95 < 150 ms on dedicated hardware.

Follow-up (same day): the spawn query's `abs()` proximity test was rewritten as `BETWEEN` ranges usable by the `cities (world_id, x, y)` index. `EXPLAIN ANALYZE` on the load-test database (204 cities): **55.1 ms → 5.9 ms**. The load test has not been re-run after this change.
