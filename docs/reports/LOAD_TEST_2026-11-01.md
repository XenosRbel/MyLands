# Load test — 2026-11-01 (1 000 players)

Task: [T-021](../../tasks/T-021.md). Previous baseline: [LOAD_TEST_2026-10-31.md](LOAD_TEST_2026-10-31.md).

## Setup

- One 4-vCPU container runs the server, PostgreSQL 16 and the load generator together.
- Database pool: 20 connections. World speed ×50. Rate limits raised.
- The world uses a copy of the Ashen Crowns pack with a 140×140 map. The shipped 48×48 map holds fewer than 256 capitals.
- Harness: `server/cmd/loadtest`. Each run used a fresh database.
- Command: `loadtest -players 1000 -duration 150s -ramp 30s -think 10s -target-p95 150ms -target-cmds 45 -target-lag 2`.
- One player acts every 10 s. Half of the actions are commands. This gives about 50 commands per second.
- Joins are spread over 30 s. The command rate is measured after the ramp plus 5 s.

## Targets and results

| Target | Run 7 | Run 8 | Run 9 | First run |
|---|---|---|---|---|
| 1 000 players, no 5xx or network error | Pass | Pass | Pass | **Fail** (105 network errors) |
| 50 commands/s (check at 45) | 45.3/s | 45.3/s | 45.3/s | 43.0/s |
| p95 below 150 ms (city, build, train) | 7 ms | 11 ms | 7.5 ms | **Fail** (city 3.9 s) |
| Worker lag below 2 s | 0 s | 0 s | 0 s | 0 s |
| Failed or parked events | 0 | 0 | 0 | 0 |

Run 9 detail: city p95 7.3 ms, build 7.5 ms, train 5.2 ms, join p95 13.3 ms, join max 25.5 ms.

The first run failed. The guest sign-in median was 6.9 s, so the host was starved before the test reached the server code.
Three runs with the same command and a fresh database then passed.
The cause of the first failure is not proven. Treat 3 of 4 as the honest pass rate on this shared host.

## Changes that produced the result

| Change | Evidence |
|---|---|
| `findSpawn` takes a per-world advisory lock | Test `TestSpawnKeepsSpacingForConcurrentJoins` failed 6 of 6 runs before the fix. Capitals stood 1 tile apart. It passes 10 of 10 runs after |
| `findSpawn` walks rings instead of sorting the whole map | `EXPLAIN ANALYZE` at 404 cities: 27 ms for the old query. One join dropped from 52 ms to 11.8 ms median after the ring hint |
| `Pack()` reads `pack_json` only on a cache miss | `pack_json` is 59 KB of `jsonb`. It was read on every call |
| `/metrics` reports `rf_events_max_lag_seconds` | Worker lag is now measurable in seconds |

Join comparison at 200 players on the 48×48 map, same command as the 2026-10-31 baseline:

| | 2026-10-31 | 2026-11-01 |
|---|---|---|
| join p95 | 1 155 ms | 486 ms |
| throughput | 648 req/s | 868 req/s |

## Limits found

- A burst of 1 000 simultaneous joins does **not** pass. Joins run one at a time per world.
- Measured join capacity is about 70 per second. 300 simultaneous joins finish in 4.2 s. 1 000 exceed the 15 s client timeout.
- One slow commit of 21 ms was seen in the database log with fsync on. The share of commit time in the 13 ms per join is not measured.
- Spreading 1 000 joins over 30 s works. Plan registration bursts, such as a launch event, around 70 joins per second per world.
- The ring hint lives in process memory. It only orders the search. It is not needed for correctness.

## Not measured

- Separate database host and dedicated hardware.
- PvP, market and alliance traffic.
- More than one server instance. The advisory lock works across instances, the ring hint does not.
- Runs longer than 150 s. Event backlog over hours is untested.
- The first failed run is unexplained.
