# API

Machine-readable contract: [`server/api/openapi.yaml`](../../server/api/openapi.yaml) (OpenAPI 3.1, 70 operations, generated by `server/api/gen_openapi.py`; `internal/api/openapi_test.go` fails if a registered route is missing from it).

## Conventions

| Aspect | Rule |
|---|---|
| Base path | `/api/v1` (version in path; breaking changes → `/api/v2`) |
| Format | JSON UTF-8. Unknown request fields are rejected (`400 invalid_json`). Body ≤ 64 KiB (`413`). |
| Success | `200 {"data": …}` |
| Error | `{"error": {"code": "machine_code", "message": "human text", "details": {...}}}` |
| Auth | `Authorization: Bearer <opaque token>` from register/login/guest/platform. Tokens are stored server-side as SHA-256 hashes; TTL `RF_SESSION_TTL` (default 30 days); logout revokes. |
| Authorization | Every handler resolves the caller's player/city from the token. Foreign city/job/mission/hero/item/order ids return **404** (existence is not revealed). Admin routes require `is_admin`. |
| Idempotency | All game commands (see `x-idempotent` in OpenAPI) require `Idempotency-Key` (8–80 `[A-Za-z0-9_-]`). Exactly-once semantics, byte-identical replay with `Idempotent-Replay: true`, `422 idempotency_key_reused` on body mismatch, 24 h retention. Auth/admin endpoints are not keyed (they are naturally idempotent or audited). |
| Rate limits | Token bucket per account (authenticated) and per IP (auth endpoints): `RF_RATE_RPS`/`RF_RATE_BURST`. `429 rate_limited` + `Retry-After`. Messages: ≤ 60/hour per player. |
| Pagination | Cursor style: `before=<id>&limit=` (reports, messages), `after=<id>` (notifications), `limit/offset` (rankings ≤ 100). Map viewport ≤ 64×64. |
| Time | All timestamps RFC 3339 UTC. `serverTime` is included in overview and city views; clients must compute countdowns from it. |
| CORS | Allow-list `RF_ALLOWED_ORIGINS` (dev Vite, Capacitor `https://localhost`). |
| Caching | `Cache-Control: no-store` for API; pack endpoint uses `ETag` = pack hash. |

HTTP mapping: 400 validation, 401 auth, 403 permission/ban, 404 missing/foreign, 409 state conflict, 422 game rule, 429 limits, 5xx infrastructure (client may retry with the same key).

## Typical flows

```text
POST /api/v1/auth/guest                       → token
GET  /api/v1/worlds                           → choose world
GET  /api/v1/worlds/{wid}/pack                → names, theme, rules data (cache by ETag)
POST /api/v1/worlds/{wid}/join {name, race}   → player + capital
GET  /api/v1/worlds/{wid}/overview            → cities, counters, serverTime
GET  /api/v1/cities/{cid}                     → resources, rates, next steps with costs/blocked reasons, queues
POST /api/v1/cities/{cid}/build {building}    + Idempotency-Key
POST /api/v1/cities/{cid}/missions {kind,x,y,units,...} + Idempotency-Key
GET  /api/v1/worlds/{wid}/reports
```

## Read endpoints settle state

`GET` endpoints for a player's own data run the same settlement as commands (process due events, advance economy) inside a transaction, so a read always returns current authoritative state even if the worker is lagging.
